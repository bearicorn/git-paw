## Context

git-paw persists six kinds of file that outlive the binary that wrote them:

| Format | Written by | Read by today |
|---|---|---|
| repo `.git-paw/config.toml` | the user, `git paw init` | `config::load_config` (no `deny_unknown_fields`, so removed keys are ignored) |
| global `config.toml` | `add-cli` / `remove-cli` | `config::load_config` |
| global session file `<data_dir>/git-paw/sessions/<name>.json` (`Session` / `WorktreeEntry`) | `start`, `add`, `remove`, `pause`, `stop` | every session command, recovery, `status --json` |
| per-repo discovery file `.git-paw/sessions/<name>.json` (`RepoSessionFile`) | `start`, `add`, `remove` | `add`/`remove` (Rust), `sweep.sh` (Python) |
| `broker.log` (one `BrokerMessage` `Display` line per entry) | the broker flush thread, append-only | nothing in the binary; `purge` deletes it |
| `.git-paw/sessions/<name>.manual-approvals.jsonl` (`ManualApproval`) | append-only; up to v0.16.0 the attended auto-approve thread's recorder, from v0.17.0 only the `--unattended` drive loop, once per escalated permission prompt (`classifier-retirement`) | `git paw approvals` |

Back-compat is tested today only by unit fixtures written by hand for one field at a time. The
`v0.16.0`, `v0.17.0` and `v0.18.0` tags exist and those releases are on crates.io, so their files
can be captured from the real binaries.

## Goals / Non-Goals

**Goals:**

- Load every format written by every release since v0.16.0 under the current build.
- Exercise the post-upgrade operations: `status`, recovery through `start`, `stop`, `purge`,
  `approvals`, and a broker appending to an old log.
- Make adding a release's row part of releasing.

**Non-Goals:**

- Versioning or migrating formats — v0.21.0 owns that. This change tests it.
- Downgrades (a file from a newer release read by an older binary). v0.21 specifies refusal.
- Live tmux state. A fixture cannot capture a running server; resuming a session that is still
  alive across an upgrade is covered by v0.18's own fallback tests.
- Fixing anything the matrix finds. Each finding is its own change.

## Decisions

### D1 — Capture from the released binary, not by hand

`tests/fixtures/compat/capture.sh <version>` installs that release into a temporary root
(`cargo install git-paw --version =<version> --locked --root <tmp>`), creates a throwaway repo with
a stub agent CLI, and runs a fixed script: `init`, enable the broker, `start` two branches,
publish a few broker messages, record one manual approval, `pause`, then `stop`. From v0.17.0 the
manual-approvals log is written only by the `--unattended` drive loop when it escalates a live
permission prompt (attended sessions write none), so for those releases "record one manual
approval" means an `--unattended` run whose stub agent shows one live permission prompt that the
loop escalates. It copies the six
files out and rewrites machine-specific values to placeholders (`{{HOME}}`, `{{REPO}}`,
`{{WORKTREE_PARENT}}`, `{{CREATED_AT}}`). Hand-written fixtures encode what the author thinks the
format is; the point here is what the binary actually wrote.

*Alternative rejected:* generating old files from the serde types at the old tag. It needs a
second build of the old crate inside the test, and still misses anything written outside serde
(the log line format, the init template).

### D2 — One test table, one row per (release, format)

`tests/upgrade_compat_matrix.rs` walks `tests/fixtures/compat/*/`, substitutes placeholders with
tempdir paths, installs the files where the current build looks for them (HOME and
`XDG_DATA_HOME` overridden per `core-ci-hygiene`, tmux socket isolated), and runs the
operations against the compiled binary. Each row reports its release and format on failure. A
release with a format missing from its directory is a failure unless the README for that release
records why the format did not exist.

### D3 — Completeness from the changelog

The guard reads the `## [X.Y.Z]` headers in `CHANGELOG.md` (generated by git-cliff at each
release) and requires a fixture directory for every version ≥ 0.16.0. The release-prep commit
therefore cannot land without the row. *Alternative rejected:* reading git tags, which a shallow
CI checkout does not have.

### D4 — "Resume" means recovery from a stopped session

The fixture's session is captured after `stop`, and also rewritten to `status = "active"` with no
tmux server, which the current build reports as stopped. `start` in that repo must rebuild the
session from the recorded entries (the existing recovery path), with each worktree's recorded CLI.
`stop` and `purge` must then clean up everything the old release created: worktrees, branches it
created, the discovery file, the global session file and `broker.log`.

From v0.21.0 the dashboard is opt-in (`dashboard-usage-view`), so a release from then on captures a
second session with the broker on and no dashboard. Recovery must rebuild the dashboard the session
recorded, not the one the current config selects; that row checks it.

### D5 — Unversioned means the baseline

Until v0.21.0 lands, the assertions are "loads with defaults for every field added since". Once
`config-schema-versioning` and `wire-format-dtos` land, an unversioned file reads as version 1
and the matrix additionally asserts that the current build does not rewrite a user's config to
migrate it.

### D6 — Deprecated no-effect keys are exempt from "no lost value"

v0.17.0 (`classifier-retirement`) kept `[supervisor.auto_approve]` and
`[supervisor.common_dev_allowlist]` parse-only: they load, warn once per file and do nothing.
v0.21.0's v1 → v2 config migration drops both tables. A v0.16.0 config is likely to carry at least
the second one, because 0.16.0 serialized a default table on every save. The "every recorded value
is the value used" assertion therefore skips keys the current build documents as deprecated with no
effect; it still requires the file to load without error and every other value to survive. The
exemption is a fixed list read from the deprecation registry once v0.21.0 has one, so it cannot
silently grow.

## Risks / Trade-offs

- [A fixture leaks the capturing machine's paths or username] → The capture script substitutes
  placeholders and fails if `$HOME`, `$USER` or the temporary root still appears in any output
  file; the README forbids committing a real config.
- [crates.io yanks or the toolchain cannot build an old release] → Fixtures are committed, so
  capture runs once per release; the README records the toolchain used.
- [The scripted session drifts from real usage] → The script exercises every writer of every
  format; a new persisted field that the script never triggers is a capture-script task for the
  release that adds it.
- [Matrix runtime grows with releases] → One row is a handful of subprocess runs; eight rows by
  v1.0.0 is well within the suite's budget.

## Open Questions

- Should the injected `AGENTS.md` boot block (stripped by `stop`/`purge` via
  `agents::remove_session_boot_block`) join the matrix? It is a persisted artifact whose markers
  must stay recognisable across releases. Recommended yes if its markers change before v1.0.0;
  today they have not, so it is not a row yet.
