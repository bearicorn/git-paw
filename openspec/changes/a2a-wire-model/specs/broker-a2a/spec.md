## ADDED Requirements

### Requirement: A2A objects serialize as A2A 1.0 ProtoJSON

The broker SHALL represent every A2A object it emits or accepts with wire types that are separate from its internal coordination model. It SHALL serialize them as the A2A 1.0 specification requires, which follows ProtoJSON:

- Field names SHALL be camelCase.
- Enum values SHALL be the proto enum names as strings, for example `"TASK_STATE_WORKING"` and `"ROLE_AGENT"`.
- Timestamps SHALL be ISO 8601 UTC strings with a `Z` suffix and millisecond precision.
- An unset optional field SHALL be omitted. It SHALL NOT be emitted as `null`.
- A `Part` SHALL carry exactly one of `text`, `raw`, `url` or `data` as its member, with no `kind` discriminator.

When deserializing, the broker SHALL ignore fields it does not recognize.

#### Scenario: Task serializes with camelCase fields and enum names

- **GIVEN** a task record for agent `feat-x` in state `WORKING` with a status timestamp of 2026-10-18T10:30:00.123Z
- **WHEN** it is mapped and serialized as an A2A `Task`
- **THEN** the JSON SHALL contain the keys `id`, `contextId` and `status`
- **AND** `status.state` SHALL equal `"TASK_STATE_WORKING"`
- **AND** `status.timestamp` SHALL equal `"2026-10-18T10:30:00.123Z"`
- **AND** the JSON SHALL contain no key `context_id` and no `null` value

#### Scenario: Text part carries no kind discriminator

- **WHEN** a status message with the text "running tests" is serialized
- **THEN** its single part SHALL serialize as `{"text":"running tests"}`

#### Scenario: Unknown input fields are ignored

- **GIVEN** an incoming A2A `Message` JSON that contains every required field plus an unknown field `"futureField": 1`
- **WHEN** it is deserialized
- **THEN** deserialization SHALL succeed
- **AND** the required fields SHALL carry the sent values

### Requirement: One A2A task per worker assignment

The broker SHALL open exactly one A2A task for a worker agent id when it first learns of that agent: from a watch-target registration, or from the first coordination message that names the agent as its sender or its target. The root identity `"orchestrator"` SHALL NOT be given a task.

Task identifiers SHALL be generated by the broker. They SHALL be unique within their context and SHALL be treated by clients as opaque. Every task opened by one broker host instance SHALL carry that instance's single `contextId`.

#### Scenario: Watch-target registration opens a submitted task

- **GIVEN** no task exists for `feat-x`
- **WHEN** a watch target for agent `feat-x` is registered
- **THEN** exactly one task for `feat-x` SHALL exist
- **AND** its state SHALL be `SUBMITTED`

#### Scenario: Root identity never becomes a task

- **WHEN** the root identity publishes `agent.status` with `agent_id = "orchestrator"`
- **THEN** no task SHALL be opened for `"orchestrator"`

#### Scenario: Two workers get distinct tasks in one context

- **WHEN** workers `feat-x` and `fix-y` each publish an `agent.status`
- **THEN** two tasks SHALL exist with different `id` values
- **AND** both SHALL carry the same `contextId`

### Requirement: Task state is projected from coordination events

The broker SHALL compute each task's A2A state by folding that worker's coordination events in broker sequence order. The rules for a task in a non-terminal state are:

- **`agent.status`** from the worker SHALL move `SUBMITTED` to `WORKING`. It SHALL leave `WORKING` and `INPUT_REQUIRED` unchanged.
- **`agent.artifact` with status `done`** SHALL move the task to `INPUT_REQUIRED`.
- **`agent.artifact` with any other status** SHALL move the task to `WORKING`.
- **`agent.blocked` or `agent.question`** sent by the worker SHALL move the task to `INPUT_REQUIRED`.
- **`agent.intent`** SHALL move `SUBMITTED` to `WORKING`. It SHALL leave every other state unchanged.
- **`agent.feedback` or `agent.answer`** targeting the worker SHALL move the task to `WORKING`.
- **`agent.verified`** targeting the worker SHALL move the task to `COMPLETED`.
- **A cancellation recorded by the broker** SHALL move the task to `CANCELED`.

The variants `agent.advanced-main`, `agent.learning` and `orchestrator.verify-now`, and any `agent.question` whose `agent_id` is the root identity, SHALL NOT change any task.

Given the same ordered events and the same timestamps, the projection SHALL produce the same task.

#### Scenario: Projection table

- **GIVEN** a task for `feat-x` in the start state of each row below
- **WHEN** the row's event is applied
- **THEN** the task SHALL be in the row's resulting state

| Start state | Event | Resulting state |
|---|---|---|
| `SUBMITTED` | `agent.status` (`working`) from `feat-x` | `WORKING` |
| `WORKING` | `agent.artifact` (`committed`) from `feat-x` | `WORKING` |
| `WORKING` | `agent.artifact` (`done`) from `feat-x` | `INPUT_REQUIRED` |
| `WORKING` | `agent.question` from `feat-x` | `INPUT_REQUIRED` |
| `WORKING` | `agent.blocked` from `feat-x` | `INPUT_REQUIRED` |
| `INPUT_REQUIRED` | `agent.status` (`working`) from `feat-x` | `INPUT_REQUIRED` |
| `INPUT_REQUIRED` | `agent.answer` to `feat-x` | `WORKING` |
| `INPUT_REQUIRED` | `agent.feedback` to `feat-x` | `WORKING` |
| `INPUT_REQUIRED` | `agent.verified` for `feat-x` | `COMPLETED` |
| `SUBMITTED` | `agent.intent` from `feat-x` | `WORKING` |
| `WORKING` | broker-recorded cancellation | `CANCELED` |

#### Scenario: Session-level events change no task

- **GIVEN** tasks for `feat-x` and `fix-y` in state `WORKING`
- **WHEN** an `agent.advanced-main`, an `agent.learning` and an `orchestrator.verify-now` are applied
- **THEN** both tasks SHALL remain `WORKING` with unchanged status messages

#### Scenario: Projection is deterministic

- **GIVEN** an ordered list of ten coordination events for `feat-x`, each with a fixed timestamp
- **WHEN** the projection is computed twice from that list
- **THEN** the two resulting tasks SHALL be equal

### Requirement: Only the verdict variant completes a task

A task SHALL reach `COMPLETED` only by applying an `agent.verified` message that targets its worker. Status labels SHALL NOT complete a task. This holds when an `agent.status` or `agent.artifact` carries a label such as `"verified"` or `"done"`, and for whatever label a worker publishes.

#### Scenario: Worker-published verified label does not complete

- **GIVEN** a task for `feat-x` in state `WORKING`
- **WHEN** `feat-x` publishes `agent.status` with `status = "verified"`
- **THEN** the task SHALL remain `WORKING`
- **AND** its extension metadata `statusLabel` SHALL be `"verified"`

#### Scenario: Worker-published verified artifact does not complete

- **GIVEN** a task for `feat-x` in state `WORKING`
- **WHEN** `feat-x` publishes `agent.artifact` with `status = "verified"`
- **THEN** the task SHALL be `WORKING`, not `COMPLETED`

### Requirement: Terminal tasks are final and new root work opens a new task

When a task is `COMPLETED` or `CANCELED`, events SHALL be handled as follows:

- Events that the worker originates SHALL NOT change the task.
- A repeated `agent.verified` SHALL NOT change the task.
- An `agent.feedback` or `agent.answer` that targets the worker SHALL open a new task for that worker, with the generation increased by one, in state `WORKING`. The new task's first history message SHALL list the previous task's id in `referenceTaskIds`. Its extension metadata SHALL carry `previousTaskId`.

From then on, the worker's events SHALL apply to the newest task.

#### Scenario: Heartbeat after completion is ignored

- **GIVEN** a `COMPLETED` task for `feat-x`
- **WHEN** `feat-x` publishes `agent.status` with `status = "working"`
- **THEN** the task SHALL remain `COMPLETED`
- **AND** no new task SHALL be opened

#### Scenario: Feedback after completion opens generation two

- **GIVEN** a `COMPLETED` task `T1` for `feat-x`
- **WHEN** an `agent.feedback` targeting `feat-x` is applied
- **THEN** a second task `T2` for `feat-x` SHALL exist in state `WORKING` with generation 2
- **AND** `T2`'s first history message SHALL list `T1`'s id in `referenceTaskIds`
- **AND** `T1` SHALL remain `COMPLETED`

### Requirement: Task status message, history and artifacts

Each worker event SHALL be reflected in the task as follows:

- Each event applied to a task SHALL set the task's status timestamp to the event's publish time.
- An `agent.status` SHALL set the status message to a `ROLE_AGENT` text message. The text SHALL be the payload's `activity` if present, else its `message`, else its status label. An `agent.status` SHALL NOT add a history entry.
- An `agent.question` SHALL be recorded in the task history as a `ROLE_AGENT` message.
- An `agent.blocked` SHALL be recorded in the task history as a `ROLE_AGENT` message.
- An `agent.artifact` with status `done` SHALL be recorded in the task history as a `ROLE_AGENT` message.
- Each `agent.artifact` SHALL also append one `Artifact`. It SHALL have one `data` part with media type `application/json` holding the artifact's status, exports and modified files.
- An `agent.answer`, `agent.feedback` or `agent.verified` SHALL be recorded in the history as a `ROLE_USER` message. The text of an `agent.feedback` message SHALL be its errors, one text part per error.

Every message the broker derives SHALL carry a `messageId` that is unique within the context.

#### Scenario: Heartbeats update the status message without growing history

- **GIVEN** a `WORKING` task for `feat-x` with an empty history
- **WHEN** `feat-x` publishes three `agent.status` messages, the last with `activity = "running tests"`
- **THEN** the status message text SHALL be "running tests" with role `ROLE_AGENT`
- **AND** the history SHALL be empty

#### Scenario: Committed artifact appended as a data part

- **WHEN** `feat-x` publishes `agent.artifact` with `status = "committed"`, `exports = ["parse"]` and `modified_files = ["src/a.rs"]`
- **THEN** the task SHALL gain one artifact whose single part is a `data` part with media type `application/json`
- **AND** that part SHALL contain the exports `["parse"]` and the modified files `["src/a.rs"]`

#### Scenario: Feedback recorded as a user message with one part per error

- **WHEN** an `agent.feedback` with errors `["test a fails", "lint b"]` targets `feat-x`
- **THEN** the task history SHALL end with a `ROLE_USER` message that has two text parts, "test a fails" and "lint b"

### Requirement: git-paw coordination extension v1

The broker SHALL identify the git-paw coordination extension by the URI `https://bearicorn.github.io/git-paw/a2a/coordination/v1`. It SHALL carry git-paw coordination facts only as metadata stored under that URI key, as follows:

- **Task metadata** SHALL carry `agentId` and `generation` and `modifiedFiles`. It SHALL carry `statusLabel` and `phase` when they are known. It SHALL carry the worker's unexpired intents as `intents`, each with `files`, `summary`, `validForSeconds` and `declaredAt`. It SHALL carry `previousTaskId` when the task is a later generation.
- **Messages the broker derives** SHALL carry an `event` field whose value is one of `status`, `artifact`, `blocked`, `question`, `intent`, `feedback`, `guidance`, `verdict` or `cancel`. An `agent.blocked` message SHALL also carry `needs` and `from`.

A breaking change to this metadata SHALL use a new URI.

#### Scenario: Task metadata carries the agent id and files

- **GIVEN** worker `feat-x` whose last `agent.status` reported `modified_files = ["src/a.rs"]`
- **WHEN** its task is serialized
- **THEN** `metadata["https://bearicorn.github.io/git-paw/a2a/coordination/v1"]` SHALL contain `agentId = "feat-x"`, `generation = 1` and `modifiedFiles = ["src/a.rs"]`

#### Scenario: Intent appears in metadata without changing state

- **GIVEN** a `WORKING` task for `feat-x`
- **WHEN** `feat-x` publishes `agent.intent` with files `["src/b.rs"]`, summary "refactor b" and `valid_for_seconds = 600`
- **THEN** the task SHALL remain `WORKING`
- **AND** its extension metadata `intents` SHALL contain one entry with `files = ["src/b.rs"]` and `validForSeconds = 600`

#### Scenario: Blocked message carries needs and from

- **WHEN** `feat-x` publishes `agent.blocked` with `needs = "api types"` and `from = "feat-y"`
- **THEN** the history message's extension metadata SHALL contain `event = "blocked"`, `needs = "api types"` and `from = "feat-y"`
